# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository purpose

`prd-manager` is a Claude Code Skill for generating and maintaining versioned project documentation. It helps users turn product ideas into a structured documentation lifecycle covering PRD, design, technical implementation, plan, ops, testing, changelog, incidents, and project-level Claude context.

This is not an application codebase. It is a Skill/package repository made primarily of Markdown templates, Skill definitions, reference docs, metadata, and evaluation fixtures.

## Common commands

There is currently no `package.json`, lockfile, Makefile, or configured build/lint/test runner in this repository.

Useful repository commands:

```bash
# Inspect repository state
git status

# Review changed documentation
git diff -- README.md SKILL.md assets/ references/ evals/

# Search Skill and template content
git grep "docs/prd"
git grep "接口影响清单"
git grep "test.md" SKILL.md assets/
```

Evaluation cases are stored as static fixtures in `evals/evals.json`. There is no repo-local command to run the full eval suite or a single eval case.

## High-level structure

- `SKILL.md` is the sole active Skill definition for `prd-manager`. It contains the v2.0.0 lifecycle workflow covering `prd.md`, `design.md`, `dev.md`, `plan.md`, `ops.md`, `test.md`, `CHANGELOG.md`, incidents, and `CLAUDE.md`.
- `README.md` is the user-facing overview, installation guide, examples, directory description, and feature summary for v2.0.0.
- `assets/` contains the document templates the Skill references when generating project artifacts:
  - `prd_template.md`, `design_template.md`, `dev_template.md`, `plan_template.md`
  - `ops_template.md`, `test_template.md`, `incident_template.md`, `changelog_template.md`, `claude_template.md`, `readme_template.md`
- `references/` contains reusable guidance the Skill points to, including priority definitions and ASCII design patterns.
- `agents/openai.yaml` contains Skill UI/agent metadata.
- `evals/evals.json` defines expected behavior scenarios for Skill validation.
- `VERSION_HISTORY.md` records version-level changes, especially the v2.0.0 expansion from template library to AI collaboration workflow engine.

## Skill behavior model

The central workflow is confirmation-gated:

```text
prd.md confirmation
  → design.md / dev.md confirmation
  → plan.md + test.md + ops.md
  → CHANGELOG.md / CLAUDE.md
  → docs/prd/README.md index update
```

Document boundaries are a core invariant:

- `prd.md`: what and why — requirements, users, goals, acceptance criteria.
- `design.md`: what it looks like — page structure, flows, components, ASCII prototypes.
- `dev.md`: how to implement — architecture, data model, APIs, file impact, database changes.
- `plan.md`: when and sequencing — tasks, milestones, owners, risks.
- `ops.md`: how to deploy and operate — env vars, deployment, monitoring, troubleshooting, rollback.
- `test.md`: how to verify — testing strategy, cases, automation, release checks.
- `CHANGELOG.md`: version-to-version changes.
- `CLAUDE.md`: AI-readable project memory and operating rules for generated target projects.

When editing Skill logic or templates, keep these boundaries aligned across `README.md`, `SKILL.md`, and `assets/*_template.md`.

## Versioned documentation architecture

The Skill supports two output layouts for projects that use it:

1. Version-first layout, usually under `docs/prd/<version>/`, where each version directory contains its PRD, design, dev, plan, ops, test, changelog, SQL scripts, and incidents.
2. Type-first layout under `docs/{prd,design,dev,plan,ops,test}/<version>/`, for projects where document types evolve independently.

`docs/prd/README.md` is treated as the version index and should be maintained in reverse chronological order when the Skill creates, expands, or archives versions.

## Important repo-specific constraints

- Do not add npm/pnpm/yarn commands unless a package manager config is actually introduced.
- Keep `SKILL.md`, `README.md`, templates, and eval expectations consistent when changing documented behavior.
- The Skill emphasizes semantic versioning: major for breaking changes, minor for compatible new functionality, patch for fixes and small improvements.
- For backend project documentation generated by this Skill, `dev.md` must include an interface impact list with added, changed, and removed APIs; use `无` for empty categories rather than omitting them.
- Database-changing documentation should generate independent SQL files under the version directory, typically `sql/DDL.sql` and `sql/DML_init.sql`.
- Priority definitions are centralized in `references/priority_definitions.md`: P0 must ship, P1 should ship, P2 can defer, P3 needs further evaluation.
